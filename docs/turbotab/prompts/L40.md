# Part A — the gap, and two rulings you asked for

**A1 · `GUIDED-125` — move the threshold now, on a passing run.** You declined to move the
resolution card's trigger last loop, citing the standing rule, and that was exactly right. **This
is the run the rule prescribes.** `LOOP.md` §06.2: correct *which quantity is gated*, on a passing
run, with the reasoning recorded before it is load-bearing — after a breach the same correction is
indistinguishable from relaxing a gate under pressure.

The arithmetic is yours and it is right: chance is `1/k`, not `0.5`, so the widest interval a
holdout can produce must be measured against the distance from `1/k` to 1. Binary fires below
`n = 15.4`; three-class should fire below `n = 9.5`. Generalize the derivation rather than special-
casing `k = 3`, and **state `k` in the card**, because a threshold that changes with the outcome's
arity and does not say so is a threshold nobody can check.

because both change what Classic reports and `LOOP.md` §08 keeps shared-core decisions off a loop's
desk. Here is the decision, so they stop being blocked.

- **`GUIDED-120`** — `ml/dataset_profile.is_id_like` requires an integer dtype and answers `False`
  for every string identifier. That is not a difference of opinion between two doors; **a string
  identifier is an identifier**, and widening the rule makes Classic *more* correct, not different.
  `ROADMAP.md` "One core, no forks" is the governing line: neither UI may hold a private copy of a
