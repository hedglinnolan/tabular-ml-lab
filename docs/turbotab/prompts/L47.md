## 02 · How to run this loop — the fan-out doctrine

**You are an Opus-class agent and you may spawn subagents. This section is the instruction set for
that and it is not optional.** Every rule below exists because this project already paid for its
absence.

### Where to fan out

`LOOP.md` §02's rule decides it, and it transfers to parallelism unchanged:

> **The test is whether the last example bent the abstraction.** A part that is *discovering a shape*
> stays narrow and deep. A part that is *filling out a shape already seen* goes as wide as you can
> hold.

- **Fan out on Part F, hard.** Independent rows against surfaces that do not touch. One subagent per
  row or per tight cluster. **Order hardest-first** — judge hardest by what is most likely to break
  the shape Part C established, not by effort — and start the hard ones first so the seam shows
  while the easy ones are unwritten.
- **Fan out on reading, anywhere, freely.** `turbotab/web/index.html` is ~6,000 lines in one file.
  Call-chain tracing, test-coverage questions, "what reads this" — parallelize all of it. Reading is
  always safe.
- **Fan out Part D's enumeration, not its judgment.** Many readers can inventory controls; one agent
  decides what the counts mean and writes the docstring that states the probe's limit.
- **Fan out Part E to two subagents**, one per finding — the surfaces genuinely do not touch. **You**
  write the class note that unifies them.
- **Do NOT fan out Parts B and C.** B is two criticals whose fixes must match existing shapes field
  for field, and matching a shape is exactly what a second agent gets wrong. **C is discovering a
  shape** — it establishes the pattern every later control in this app copies, and a shape discovered
  by four agents in parallel is four shapes. Build C yourself, once, then let F copy it.

### The rules a subagent must never break

1. **`data/findings.json` and `register.json` have exactly one writer: you, serially, through
   `ledger.py` / `register.py`.** No subagent runs `add`, `set`, or `regen`. Collect proposed rows as
   text in subagent reports and file them yourself. `ledger.py` serializes at `indent=1`; a script
   that dumps at `indent=2` reformats nine thousand lines — **a PM and an execution agent have each
   already done exactly that**, and both were caught by a human reading a diffstat.
2. **No subagent commits.** Commits are yours, one per part, staging **explicit paths**, `git status`
   first. **Never `git add -A`.**
3. **No subagent runs a full suite.** `TEST-040`: four job-polling sites spin a bounded loop with no
   wait and assert `status == "done"`, so **concurrent pytest runs manufacture failures**. Targeted
   single-file runs are fine. The full counts are yours, once, serially, at the end.
4. **Two subagents must never edit the same file.** Most of this loop touches
   `turbotab/web/index.html`. **Serialize every edit to it through yourself** — a subagent working on
   that file returns a diff or an instruction and does not apply one.
5. **A subagent that finds something outside its brief reports it and does not act.** L41's best
   result came from going outside the parts, and it was right *because it was reported first*.

### What a subagent must be told

The finding id, the file and line its row names, the governing doc section, **which existing
instance the fix must match by name**, and *report file:line for every claim*. A subagent prompt
that says *"fix `GUIDED-158`"* has handed it the job of deciding what the science is —
`LOOP.md` §02, **name the source, not the goal.**
