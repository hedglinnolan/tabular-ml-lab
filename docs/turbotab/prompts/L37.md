# Part B — the seal says what a holdout this size can resolve

**`GUIDED-102`, and this is the loop's reason. A shipped step contradicts its own specification.**

`engine.draw_holdout`'s fraction is a **constant `0.15` with no *n* term.** Driven on
`metabolomics_untargeted.csv` — n=80, `PRODUCT_VISION.md`'s own worked case — the seal draws **11
held-out rows** and says: *"11 rows (15%) are held out and will not be looked at again until the
models are scored."* True, and the only thing said. Eleven probes for any mention of a confidence
interval, bootstrap, optimism correction or instability all come back absent.

**What `PRODUCT_VISION.md`:296 specifies.** A 20% test set at n=80 is 16 rows, and a C-statistic
on 16 rows has a confidence interval spanning most of the unit interval — *an honest number that
answers nothing.* The clinical thread is direct that a single train/test split is the weakest
option at typical sample sizes and that bootstrap optimism correction is preferred because it uses
all the data. So **whether to draw a holdout at all is a consequence card at the seal, not a
default** — the same treatment the constitution gives every choice whose cost is invisible when it
is made.

**Sources, read them before building:**

- `research/CLINICAL_SURVEY_PACK.md` **§A5.4** — Riley et al.'s minimum sample size, three criteria
  for binary outcomes, and **candidate parameters, not variables** (a 4-knot spline is 3).
  §504–507 has Riley & Collins on bootstrap internal validation and the **instability plots**.
- `research/METABOLOMICS_PACK.md` **§751** — the detectable-effect-size curve given n, α after FDR
  and observed CV, *explicitly preferred over a post-hoc power figure.*
- `research/NUTRITION_PACK.md` **§254–259** — λ and the attenuation penalty.

**Four rules, and they are what make this not a refusal.**

1. **It never says "don't."** No refusal, no blocked step, no gate. A researcher who wants a
   holdout at n=80 gets one. The app states what that study can see and records the sentence.
2. **It states the instrument's resolution, never a verdict on the claim.** *"A C-statistic
   estimated on 11 rows has a confidence interval spanning most of the unit interval"* is
   arithmetic over what the app holds. *"This study is underpowered"* is **post-hoc power in a
   nicer suit** — listed flatly as an anti-pattern in `METABOLOMICS_PACK.md` §10 — and we would be
   committing a named error while presenting as the tool that catches them. Do not write it.
3. **It fires only when stark**, per `PRODUCT_VISION.md` §04's push-the-notable. A card that
   appears on every dataset is wallpaper. Derive the trigger from the arithmetic — Riley's
   criteria against the declared parameter count, or a holdout whose size makes the metric's
   interval useless — not from a round number someone picked.
4. **It is a recorded decision and it belongs in the manuscript.** Report exists now, so the
   sentence lands in the methods section the same loop it is written.

**Deliberately out of scope:** the full resolution statement (`PRODUCT_VISION.md`, specified-unbuilt)
and the prediction-instability plot. This part is the consequence card at the seal — smaller, about
a step that already ships, and the half that changes what a user does.

# Part C — the sensitivity fork, routed rather than built

**`MISC-014`, and the product owner has ruled: this is exposure, not construction.**

`DOMAIN_SCIENCE.md` §03 names the sensitivity fork as primitive #4, *"the highest-value cheap
addition by three of four threads, and currently absent from the app entirely."* **The last clause
is false.** `ml/sensitivity.py` (132 lines) re-runs the pipeline under varying imputation
strategies, seeds, outlier thresholds and feature subsets and exposes `is_robust(metric,
tolerance)`. `pages/08_Sensitivity_Analysis.py` (568 lines) is a shipped page over it.
`ml/publication.py` already writes the result into the manuscript. `FEATURE_PARITY.md` §1 lists it
as shared, with the line count. **Two documents in this folder contradict each other.**

**Correct the sentence in `DOMAIN_SCIENCE.md` as part of this — a design doc that asserts something
false is the governing rule failing in the place the rule is written down.**

Then route it: Guided asks the fork, the engine runs it, the answer reaches the record and the
methods section. Which of the four variation axes the fork offers is the design question — pick and
justify, do not offer all four because they exist.

**And do not inherit the defect.** `STATE-013` is open against the Classic page: seed sensitivity
**pools train+val+test and re-splits**, dissolving the lockbox, and the resulting numbers are
rendered beside lockbox-derived metrics. Guided's fork runs inside the seal or it does not run.
`STATE-034` is also open there — two independent robustness verdict systems that can contradict
each other on the same screen. One verdict.

# Part D — the gate: a specification is a claim, and a claim needs a record

**`MISC-015` and `MISC-016`. The product owner has ruled yes.** This is the audit slot, and like
L35-E it should end as an instrument rather than a fix.

**The gap.** Four of `DOMAIN_SCIENCE.md`'s seven primitives have **zero** ledger rows — hard stops,
the sensitivity fork, the checklist engine, the generalized leakage detector — tracked in one line
of prose inside an ASCII diagram. Two of the eight signature figures are in the same state:
**Kaplan–Meier**, whose numbers-at-risk table §02 marks *mandatory*, and the **forest plot**, whose
log-scale x-axis it marks *non-negotiable*. Both clinical — the pack with the largest research file
and zero detectors.

**Why it is not bookkeeping:** every number this project reports about itself comes from the
ledger. None of these is in that denominator, so the burn-down cannot see them and no report will
ever say they went missing. It is `LOOP.md` §05's habit one level up — specified in a document,
never built, never filed — and invisible to the instrument built to catch the code version.

**Build two gates:**

1. **Every primitive, signature figure and named detector in `DOMAIN_SCIENCE.md` has a ledger row**
   — filed when specified, not when someone decides to build it. Add the missing rows, then a check
   that fails when a new one is specified without one.
2. **Every page under `pages/` has a `FEATURE_REGISTER.md` row, or an explicit exemption with a
   reason in the same file.** `pages/08` and `pages/09` have none, and `register.py check`
   validates row schema only. The register's own contract makes this meaningful: `classic-only` is
   *"a claim to be justified, never a shrug"*, so an absent row is a shrug by default and the
   register cannot tell *we decided Guided will not do hypothesis testing* from *nobody considered
   it*.

**`pages/11_Theory_Reference` is exempt and is the model for how to write one:** it has no register
rows and is correctly dispositioned as a content asset in `ARCHITECTURE.md`, `METHODOLOGY.md`,
`ROADMAP.md` and `DESIGN_LANGUAGE.md` §10. The exemption records that, with the pointers.

**Report the counts**, as L35-E did: items specified, items with rows, rows added, exemptions
written. A sweep that reports only what it fixed has not reported its coverage.
